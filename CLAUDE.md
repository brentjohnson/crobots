# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CROBOTS is the original 1985 game by Tom Poindexter (GPLv2). Players write robot
control programs in a restricted subset of C; the game **compiles** each program,
loads it into a **virtual computer**, and runs up to four robots against each other
on a 1000×1000-meter battlefield, either with a live text/curses display or in
headless batch matches. All source is C (K&R style) plus a yacc grammar and a lex
scanner. It targets three eras: modern Unix (curses), PC-DOS text, and PC-DOS ANSI.

## Build & run

Build from the repo root with the top-level `Makefile` (sources stay in `src/`).
It needs `bison`, `flex`, and ncurses (found via `pkg-config`, falling back to
`-lcurses`).

```sh
make            # -> ./crobots, -O2 -Wall -Wextra, zero warnings
make clean      # removes objects, .d files, generated grammar.c/lexanal.c/tokens.h, crobots
make test       # non-interactive smoke test: -c, -m5, and -d against src/rabbit.r
```

`src/makefile.unx` is the original 1985 Unix makefile, kept only as a historical
artifact — it invokes `yacc` (not installed on modern Linux) and predates
bison/flex/pkg-config. Don't build with it; use the top-level `Makefile`.

There are no automated tests beyond `make test`. Deeper verification is manual: run
robots and watch a live battle, or run headless matches (below). Sample robots (`.r`)
live in both `src/` and `bin/`; `bin/CROBOTS.EXE` is the prebuilt DOS binary (run via
`bin/crobots_dosbox.sh`).

Run modes (after building `./crobots`):

```sh
./crobots src/robot1.r src/robot2.r  # live curses battle (2-4 robots)
./crobots -m100 r1.r r2.r            # run 100 headless matches, print win/tie tally
./crobots -c robot.r                 # compile only, print full compiler diagnostics
./crobots -d robot.r                 # single-step/trace one robot in the VM
./crobots -l50000 ...                # cap background cycles per match (default 500000)
```

The program prints a banner and waits for `<enter>` at startup (`getchar()` in
`main.c`); it is interactive by design, except `match()`'s compile loop, which makes
`-m` scriptable (e.g. `printf '\n' | ./crobots -m5 r1.r r2.r`).

### Build state

The build is clean on modern Linux/glibc (verified on GCC 16, which defaults to
`-std=gnu23` — a standard that rejects K&R function definitions outright). The
original 1985 K&R source has been converted to ANSI/C99 prototypes throughout. Two
real bugs surfaced and were fixed during that port, both worth knowing about if you
touch the VM or the front end again:

- **`match()`/`trace()` didn't set `yyin`** before `yyparse()` (`main.c`), so those two
  run modes compiled *stdin* instead of the robot file. `play()`/`comp()` were already
  correct. If you add a new call site that invokes the parser, set `yyin = f_in;` first.
- **`EXTERNAL` (`0x8000`) masking was sign-extension-broken** on any platform where
  `int` is wider than the `short int var1`/`var2` instruction fields (i.e. every modern
  platform — the original code assumed 16-bit `int`). `var1 & ~EXTERNAL` on a
  sign-extended negative short doesn't clear just the flag bit; it corrupts the offset,
  which was the actual cause of the historical "segfaults before battle ends" (any
  robot with file-scope/external variables — e.g. `src/sniper.r` — would crash on its
  first external-variable access). Fixed in `cpu.c`/`compiler.c` by widening through
  `(unsigned short)` before the mask so it zero-extends instead of sign-extends. If you
  see this pattern (`short_field & ~SOME_FLAG`) elsewhere, apply the same widening.

## Architecture

The engine is a compile-then-interpret pipeline. A robot `.r` source is parsed into
a custom stack-machine instruction stream, then all robots are round-robin executed
one instruction at a time by a shared scheduler.

**Compiler front end** — `grammar.y` (bison) + `lexanal.l` (flex) drive `compiler.c`.
The parser's semantic actions emit `struct instr` opcodes directly (there is no
separate AST); every action-called function in `compiler.c` is declared in
`compiler.h` so `grammar.y` can call across the two translation units. `compiler.h`
also holds the compiler's global symbol tables and fixup stacks. `grammar.c`,
`lexanal.c`, and `tokens.h` are generated by the top-level `Makefile` and are not
committed (see `.gitignore`).

**Virtual machine** — `cpu.c` interprets the instruction set (defined in `crobots.h`:
`FETCH`, `STORE`, `CONST`, `BINOP`, `FCALL`, `RETSUB`, `BRANCH`, etc.) over a per-robot
stack. Each robot is a `struct robot` (in `crobots.h`) carrying its own code, stack,
instruction pointer, external-variable pool, and physical state (position ×100,
heading, speed, damage). `EXTERNAL` (0x8000) is OR'd into variable offsets to mark
globals.

**Intrinsics** — `intrins.c` implements the "hardware" functions robots call:
`scan`, `cannon`, `drive`, `damage`, `speed`, `loc_x`, `loc_y`, `rand`, and trig
(`sin`/`cos`/`tan`/`atan`/`sqrt`). They are registered in the `intrinsics[]` table in
`crobots.h` and, per the calling convention, **every intrinsic must push one `long`
onto the VM stack**. Coordinate/angle convention (see `intrins.c` header): 0°=east,
90°=north; origin (0,0) is lower-left; trig results are scaled ×100000.

**Physics** — `motion.c` advances robot and missile positions each motion cycle and
applies collision/explosion damage (`DIRECT_HIT`/`NEAR_HIT`/`FAR_HIT`/`COLLISION`
constants in `crobots.h`).

**Scheduler / top level** — `main.c` owns `play()` (live), `match()` (headless), and
`trace()` (debug). The core loop gives each active robot one VM `cycle()` per pass,
then updates motion every `MOTION_CYCLES` and the display every `UPDATE_CYCLES`. A VM
error (stack overflow/underflow, missing function) sets the global `r_flag`, which
unwinds and restarts the robot's `main` with a clean stack rather than crashing.

**Display layer, swappable by platform** — `display.c` is the high-level, portable
display logic; it calls into a low-level backend that you swap per target. Exactly one
backend is linked:
- `screen.c` — curses (the only backend the top-level `Makefile` builds).
- `screend.c` — PC-DOS direct text mode (`src/makefile.unx`'s `dos` target; untouched,
  still K&R, not buildable on Linux).
- `screena.c` — PC-DOS ANSI/color (`src/makefile.unx`'s `dosa` target; same caveats).

The backend prototypes (`draw_field`, `plot_robot`, `plot_miss`, `plot_exp`) live in
`crobots.h` since `display.c` needs them regardless of backend; the DOS backends
predate that and aren't guaranteed to match if anyone ever builds them.

### Tunable constants

Gameplay and VM limits are `#define`s at the top of `crobots.h` — `MAXROBOTS`,
`CODESPACE`, `DATASPACE`, `CYCLE_LIMIT`, `ROBOT_SPEED`, missile speed/range/damage,
battlefield size (`MAX_X`/`MAX_Y`/`CLICK`). Change behavior there, not in scattered
literals.

### The `INIT`/`EXT` single-definition pattern

`crobots.h` and `compiler.h` declare globals as `extern` unless a defining flag is set,
so exactly one translation unit provides storage. `main.c` `#define INIT 1` before
including `crobots.h` (this also instantiates the `intrinsics[]` table); one compiler
module defines `EXT` for `compiler.h`. When adding a global, follow this idiom or you
get duplicate-symbol / missing-symbol link errors.

## Conventions

The `.r` files are robot programs in CROBOTS-C, **not** host C — they are data compiled
by this engine, not built by the Makefile. The language is a limited C subset
(see `docs/crobots_manual.html` and `src/crobots.doc` for the full spec); robots
typically define their own helpers like `distance()` and `plot_course()` on top of the
intrinsics. Host C (outside the untouched DOS backends) is ANSI/C99-prototyped
throughout — match that style for new code.
